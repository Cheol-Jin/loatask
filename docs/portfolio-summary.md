## 2. 서비스 목표

캐릭터 검색 후 기본 정보뿐 아니라 장비·보석·각인·스킬을 살펴보고, 같은 원정대의 다른 캐릭터로 이동하는 흐름을 만들었습니다. 첫 화면은 검색 전에도 공식 공지·이벤트·즐겨찾기·누적 검색을 볼 수 있게 구성했습니다. 게임 기능 외에 카드 운세로 가볍게 재방문할 요소를 추가했습니다.

로아와/로펙의 모든 기능을 구현한 서비스는 아닙니다. 독자적인 딜 계산이나 게임 전체 랭킹을 제공하지 않습니다.

## 3. 주요 구현

### 캐릭터 검색과 상세정보

- 공식 API의 응답을 백엔드 DTO로 매핑하고 프론트에 필요한 모델로 전달.
- 기본 프로필, 전투력·전투 특성·성향, 장비·품질·옵션, 각인, 보석, 카드/세트, 스킬/트라이포드/룬, 아크 패시브 표시.
- 장비·스킬 설명은 HTML을 실행하지 않고 텍스트로 변환.
- URL 검색어 유지, 새로고침 조회, 오류별 안내·재시도.
- 늦게 도착한 이전 요청이 최신 검색 결과를 덮지 않도록 요청 번호 확인.

### 원정대 캐릭터 목록

- 공식 계정 캐릭터 목록 API를 연동.
- 같은 서버를 기본 선택하고, 다른 서버/전체 서버를 브라우저에서 필터링.
- 아이템 레벨 문자열의 쉼표를 제거해 숫자로 정렬하고 현재 캐릭터 표시.
- 목록 실패가 상세 프로필 전체를 가리지 않도록 독립 요청과 재시도.
- 목록을 여는 것만으로 검색 횟수를 증가시키지 않음.
- [구현과 검증](character-roster.md)

### 브라우저 상태 관리

- 즐겨찾기와 성공한 최근 검색 5개를 localStorage에 보관.
- Pinia로 화면 상태를 관리하고 저장 실패를 성공으로 표시하지 않음.
- 운세 카드 36장과 세 주제별 해석 108개.
- 주제마다 KST 기준 하루 2회, 마지막 결과 복원, 재추첨 시 첫 카드 제외.
- 지원 브라우저에서 Web Locks로 여러 탭의 추첨 저장을 직렬화.
- 브라우저 데이터 삭제나 다른 기기까지 막는 계정 제한은 아님.
- [운세 상태 설계](fortune-daily-limit.md)

### 홈 화면과 외부 정보

- 공식 공지 최신 5개와 진행 중 이벤트 표시.
- 즐겨찾기, 최근 검색, 누적 검색 TOP 5, 운세 남은 횟수와 바로가기.
- 검색어 없는 홈과 기존 query 검색 주소를 모두 유지.
- 공지·이벤트를 각각 10분 캐시하고, 실패 영역만 재시도.
- [홈 구조](home-page.md)

## 4. 외부 API 성능·안정성 개선

### 문제

동일한 캐릭터를 반복 조회할 때마다 공식 API를 호출하면 외부 지연과 요청 제한에 영향을 받습니다. 단순히 캐시를 추가하는 것 외에 갱신 시점, 오류 처리, 메모리 한도, 동시 요청을 함께 고려했습니다.

### 구현

- 이름의 앞뒤 공백을 제거한 키 사용. 프로필·상세·원정대 목록은 별도 캐시.
- 성공 응답 60초 재사용, 만료 후 다음 요청에서 갱신.
- 개수 제한 및 가장 오래 사용하지 않은 항목 제거.
- 같은 키의 진행 중인 갱신은 CompletableFuture로 공유.
- 연결 오류·429·5xx면 10분 미만의 마지막 성공 응답으로 대체하고 15초 재호출 유예.
- 404·인증 오류·잘못된 응답은 이전 데이터로 감추지 않음.
- 갱신 실패 시 마지막 성공 시점을 연장하지 않음.
- 캐시 적중·미적중·병합·이전 데이터 반환과 외부 시간·오류를 종류별 로그로 기록.

### 비교 수치와 해석

2026-11-11, 같은 캐릭터 순차 조회 20회, 모의 외부 응답 지연 80ms, 첫 조회 포함:

| 조건 | 모의 외부 호출 | 평균 백엔드 클라이언트 처리 시간 |
| --- | ---: | ---: |
| 매 요청 캐시 만료를 재현한 기준선 | 20 | 87.848ms |
| 첫 조회 후 캐시 재사용 | 1 | 5.547ms |

**이 조건에서 외부 호출 95% 감소.** 실제 운영 네트워크·DB 집계·브라우저 렌더링은 제외됐습니다. 따라서 '운영 사이트 전체 응답 속도 95% 개선'이라고 쓰면 안 됩니다.

2026-11-12에는 별도 모의 40ms 지연 조건에서 같은 캐릭터 20회는 외부 호출 1회, 서로 다른 캐릭터 20회는 20회임을 지표로 확인했습니다. 이것은 서로 다른 조회 패턴의 비교이며, 같은 조건의 최적화 전후 측정으로 섞어 쓰지 않습니다.

- [실험 조건·재현 명령](character-cache.md)
- [지표 정의·운영 측정 절차](character-api-metrics.md)
- 실제 운영 트래픽의 전후 성능 비교는 미수행입니다.

## 5. 배포·오류 해결 경험

### 로컬과 배포의 차이

- Vercel npm ci의 의존성 충돌 해결: oxlint와 eslint-plugin-oxlint의 호환 버전을 맞추고 lockfile 갱신.
- 특정 운영체제 네이티브 패키지의 직접 의존을 정리해 배포 환경에서 플랫폼에 맞는 패키지 선택.
- 로컬 변경으로 가려져 있던 Git의 빈 Vue 컴포넌트와 존재하지 않는 컴포넌트 참조 수정.
- 프론트 API 주소를 환경변수로 설정하고 운영에서 방문자 localhost로 요청하지 않도록 처리.

### HTTPS와 DB 인증서

DB CA만 신뢰하는 Java truststore 구성은 DB 연결에는 맞았지만 외부 공식 API의 공인 인증서 연결을 방해했습니다. Codex가 TLS 실패를 재현하고 기본 공인 CA를 유지한 뒤 DB CA를 추가하는 방식으로 수정했습니다. 인증서 검증을 끄지 않았으며, 배포 후 실제 캐릭터 조회 200과 화면 표시를 확인했습니다.

### 무료 서비스 운영 제약

Aiven DB가 Powered off인 상태에서 Render가 DB 주소에 연결하지 못하는 상황을 확인했습니다. 사용자가 DB를 켠 뒤 서버 재시작 및 응답 확인을 진행했습니다. 무료 서버 기동 지연과 외부 DB 상태도 함께 살펴야 한다는 운영 사례입니다. 유료 서비스 수준의 가용성을 확보했다고 주장하지 않습니다.

## 6. AI 활용 과정에서 보여줄 내용

- 요구를 기능 단위로 구체화: 기존 변경 보존, main 허용, 비밀값 미출력, 무료 배포, 운세 횟수 등.
- 실제 사용 문제를 보고하고 재확인을 요청: 프로필 미표시, 로딩 지속, 홈 정보 미표시.
- 생성 결과의 오류 수정 기록: DTO 필드, 기본 인증서 보존, 트라이포드 0→1 인덱스 표시, 배포 의존성.
- 빌드와 단위/통합 테스트, 모의 비교, 실제 화면 확인의 범위를 나눠 기록.
- TASK_PROGRESS.md에 완료·변경 파일·미완료·다음 순서를 남겨 중단 후 재개.

**역할 표현 예시:** 'Codex의 구현 지원을 받아 개인 서비스를 개발하면서 요구사항을 구체화하고, 사용 중 발견한 문제와 검증 결과를 연결해 개선 과정을 정리했습니다.'

**추가 확인이 필요한 표현:** '직접 동시성 코드를 설계했다', '모든 테스트를 직접 작성했다', '운영 지표로 개선 효과를 증명했다'. 실제 본인이 수행한 범위가 아니면 쓰지 않습니다.

## 7. 자기소개서 초안

아래 문장은 지원 전에 읽고 직접 설명할 수 있는 내용만 남기세요. 글자 수 제한에 맞춘 최종본은 아닙니다.

### A. 프로젝트 소개 중심

로스트아크 캐릭터 검색 서비스 LoaTask를 개인 프로젝트로 개발했습니다. Codex의 구현 지원을 받아 요구사항을 단계적으로 구체화했으며, 기본 검색에서 장비·각인·보석·스킬을 확인하는 상세 화면과 원정대 캐릭터 간 이동으로 기능을 확장했습니다. 검색 전에도 공식 공지와 이벤트, 즐겨찾기, 최근 검색을 확인할 수 있도록 홈 화면을 구성하고 Vercel·Render·Aiven에 프론트엔드, Java API, DB를 나누어 배포했습니다. 개발 과정에서는 로컬 빌드 성공과 실제 배포 동작이 다를 수 있다는 점을 경험했습니다. 의존성 충돌, 응답 필드 매핑, HTTPS 인증서 구성 등 실제 문제의 수정 커밋과 검증 범위를 기록하며 기능 구현부터 배포 확인까지 이어지는 개발 과정을 정리했습니다.

### B. 성능 개선 중심

LoaTask의 캐릭터 조회는 같은 이름을 반복 검색해도 공식 API를 매번 호출하는 구조였습니다. 저는 이를 개선 과제로 정하고 Codex와 함께 캐시와 검증 방식을 구체화했습니다. 성공 응답을 60초간 재사용하고 같은 캐릭터의 동시 갱신 요청을 병합했으며, 연결 오류나 요청 제한이 발생하면 유효 범위 안의 마지막 성공 응답을 제공하도록 구현했습니다. 효과는 모의 API의 응답 지연을 80ms로 고정하고 동일 캐릭터를 20회 조회해 비교했습니다. 외부 호출은 20회에서 1회, 평균 백엔드 클라이언트 처리 시간은 87.848ms에서 5.547ms로 줄었습니다. 운영 사이트 전체 성능으로 확대 해석하지 않고 측정 조건과 한계를 함께 문서화했으며, 이후 실제 호출·오류·적중률을 확인할 수 있는 로그 집계를 추가했습니다.

### C. AI 활용·문제 해결 중심

LoaTask 개발에서 Codex를 코드 작성과 검증을 돕는 도구로 활용했습니다. 저는 기존 변경 보존과 비밀값 보호, 기능 범위 등 요구사항을 전달하고, 실제 사용 중 프로필이나 홈 데이터가 표시되지 않는 문제를 보고하며 재확인을 요청했습니다. 구현 과정에서는 응답 필드 이름 차이와 배포 의존성 충돌뿐 아니라 DB용 인증서 설정이 다른 HTTPS 연결을 방해하는 문제도 발견됐습니다. Codex가 재현·수정을 수행한 과정과 커밋, 테스트 결과를 연결해 기록했습니다. 또한 모의 API 테스트 성공과 실제 화면 확인을 구분하고, 최초 실패 원인이 확정되지 않은 사례는 추정으로 남겼습니다. 생성된 코드의 존재보다 어떤 근거로 동작을 확인했는지를 설명할 수 있도록 개발 기록을 체계화하고 있습니다.

## 8. 이력서용 짧은 문장

- Codex와 함께 Vue·Spring Boot 기반 로스트아크 정보 서비스를 개발하고 Vercel·Render·Aiven에 분리 배포.
- 캐릭터 응답 메모리 캐시·동시 갱신 병합·일시 장애 대체 응답 구현. 모의 API 동일 캐릭터 20회 조회에서 외부 호출 20→1회 확인.
- 캐시 적중·미적중·외부 호출 지연·429/5xx·이전 응답 반환을 종류별 로그로 집계하고 측정 범위 문서화.
- Pinia/localStorage 기반 즐겨찾기·최근 검색·KST 일일 추첨 제한 구현 및 저장 실패/날짜 경계 검증.

개발자의 개인 기여를 묻는 양식에서는 이 문장만 쓰지 말고 본인이 직접 작성·검토·재현한 부분을 이어서 명시하세요.

## 9. 면접 대비 질문

1. 왜 Redis가 아니라 메모리 캐시로 시작했나요?
   - 별도 운영 서비스를 늘리지 않고 단일 서버에서 반복 조회를 줄이는 목적이었습니다. 재시작 시 소실과 서버 간 미공유 한계가 있습니다.
2. 60초가 지나면 즉시 API를 호출하나요?
   - 아니요. 다음 조회가 들어올 때 갱신합니다.
3. 미적중 수와 외부 호출 수가 왜 다를 수 있나요?
   - 같은 키의 동시 미적중 요청은 하나의 갱신을 공유할 수 있습니다.
4. 429를 받았는데 사용자에게 200을 줄 수 있나요?
   - 허용된 나이의 기존 응답이 있으면 가능합니다. 외부 오류와 이전 데이터 반환은 지표에 따로 남습니다.
5. 인증 오류에서도 기존 데이터를 주나요?
   - 숨기지 않습니다. 일시 장애와 구분합니다.
6. 캐시 적중률이 높으면 항상 좋은가요?
   - 재호출 유예 중 이전 데이터를 반환해도 적중할 수 있어 staleResponses·외부 오류를 함께 봐야 합니다.
7. 테스트 60개면 모든 문제를 막나요?
   - 아닙니다. 마지막 코드 변경 시점의 통과 개수일 뿐, 커버리지 100%나 운영 무장애를 의미하지 않습니다.
8. 운세 하루 두 번은 다른 브라우저에서도 강제되나요?
   - 아닙니다. 브라우저 저장소 기준이며 엄격한 계정 제한은 로그인과 서버 저장이 필요합니다.
9. AI가 한 부분과 본인이 한 부분은?
   - 이 문서 6절을 기준으로 답하고, 직접 읽거나 실행한 내용은 별도 기록으로 보완합니다.
