# 오류 해결 및 재발 방지 기록

이 문서는 실제 발생한 오류와 수정 근거를 모아 두는 개발 기록입니다. 같은 증상이 생기면 먼저 해당 기록을 읽고, 기존 해결 방법과 테스트를 확인합니다. 진행 중 작업은 [TASK_PROGRESS.md](../TASK_PROGRESS.md)에, 확인이 끝난 원인과 재발 방지 기준은 여기에 남깁니다.

## 기록 원칙

- 관찰한 사실, 원인에 대한 판단, 아직 확인하지 못한 부분을 구분합니다.
- 로그·실측 수치·관련 커밋·회귀 테스트를 연결합니다. 과거 측정치는 현재 성능 보장이 아닙니다.
- API 키·비밀번호·접속 URI·환경변수 값·개인 계정 정보는 기록하지 않습니다. 원본 로그를 통째로 붙이지 않습니다.
- 운영 요청은 HTTP 메서드만으로 안전성을 판단하지 않습니다. GET도 검색 통계와 스냅샷을 저장할 수 있습니다. 재현은 로컬/모의 서버를 우선합니다.
- 문제가 해결되지 않았거나 운영 검증이 빠졌다면 그 범위를 명시합니다.

## ERR-001 — 캐릭터 검색이 2분 이상 로딩되는 현상

- 기록일: 2026-11-20 (한국 시간)
- 사용자 제보: `이다` 검색 후 2분 이상 결과가 나타나지 않음
- 수정 커밋: [d223630](https://github.com/Cheol-Jin/loatask/commit/d223630)
- 상태: 대기·취소 처리 수정 및 Vercel 배포 완료. 실제 운영 `이다` 프로필 응답은 미검증.

### 확인한 근거와 원인 판단

| 확인 항목 | 당시 결과 | 의미 |
| --- | --- | --- |
| Render 앱 시작 로그 | 앱 기동 111.802초, 프로세스 실행 후 122.199초 | 절전 후 준비 시간이 기존 90초 요청 제한보다 김 |
| 기동 이후 PROFILE 처리 로그 | 완료 2건, 실패 0건, 상위 API 호출 1회, 요청 최대 약 11.14초 | 기동 후 프로필 처리는 성공했으나 로그에 캐릭터명이 없어 `이다`의 성공으로 단정할 수 없음 |
| 운영 `/status` | HTTP 200, 약 0.21초 | 확인 당시 앱이 이미 준비된 상태였음 |
| 운영 `/search/rankings` | HTTP 200, 약 1.86초 | 확인 당시 DB 읽기 가능. DB 전체 장애로 단정할 근거 없음 |

서버 시작 대기와 실제 캐릭터 조회를 하나의 요청 제한으로 처리한 것이 문제를 일으킬 수 있는 구조였습니다. 로그에서 확인한 기동 지연이 사용자 증상과 부합하지만, 해당 사용자의 브라우저 요청과 서버 로그를 직접 연결해 재현한 것은 아닙니다.

### 수정 내용과 담당 파일

| 파일 | 바꾼 내용 | 재발 방지 목적 |
| --- | --- | --- |
| [backendReadiness.ts](../frontend/src/utils/backendReadiness.ts) | `/status`의 정상 응답을 최대 180초 확인. 개별 확인은 10초 제한, 재시도 간격 1.5초. HTML·503·네트워크 오류는 재확인하고 400/401/403/404는 설정 오류로 종료 | 시작 중 응답을 실제 준비 완료로 오인하지 않음 |
| [lostarkApi.ts](../frontend/src/api/lostarkApi.ts) | 배포 환경에서 준비 확인을 제공하고 프로필 요청에 취소 신호와 별도 30초 제한 적용 | 서버 시작 대기와 데이터 조회의 시간 제한을 분리 |
| [characterStore.ts](../frontend/src/stores/characterStore.ts) | 준비 확인 → 프로필 조회 순서, 경과 시간·단계 관리, 새 검색/취소 시 이전 요청 중단, 요청 번호로 늦은 응답 무시 | 중복 요청과 결과 덮어쓰기, 끝나지 않는 로딩 방지 |
| [CharacterListView.vue](../frontend/src/views/CharacterListView.vue) | 대기 단계·경과 시간·절전 안내·검색 취소 버튼 표시. 화면을 떠나면 요청 취소. 실패·취소 후 불필요한 순위 조회 생략 | 기다리는 이유와 종료 방법 제공 |

`AbortSignal.any()`로 사용자 취소와 시간 제한을 묶었습니다. 취소는 오류 안내와 구분하며, 타이머와 로딩 상태도 정리합니다. 개발 모드에서는 준비 확인을 건너뛰므로 기동 대기 화면 검증은 모의 API를 연결한 프로덕션 빌드에서 진행해야 합니다.

### 실제 검증 결과

- 프론트 테스트 91개 통과. 이번에 추가한 테스트 10개 포함.
- TypeScript 타입 검사와 프로덕션 빌드 통과. 기존 사용자 변경을 제외하고 실제 커밋되는 소스만 임시 폴더로 내보내 빌드한 결과도 통과.
- 로컬 모의 서버에서 21초 대기 안내·경과 시간 표시, 대기 중 프로필 호출 0회, 취소 즉시 로딩 종료, 재검색 후 `이다`라는 이름의 **모의 프로필** 표시 확인. 브라우저 콘솔 오류 0건.
- Vercel 구현 커밋 배포 성공 및 공개 JavaScript 번들에 안내·취소 버튼 반영 확인.
- 회귀 테스트: [backendReadiness.test.mjs](../frontend/tests/backendReadiness.test.mjs), [characterStore.test.mjs](../frontend/tests/characterStore.test.mjs).

### 검증하지 않은 부분과 남은 한계

- 운영 캐릭터 조회는 검색 횟수·스냅샷 DB 쓰기가 있어 실행하지 않았습니다. 모의 프로필 표시 성공을 실제 운영 캐릭터 조회 성공으로 표현하지 않습니다.
- 무료 서버의 절전과 최초 기동 시간 자체를 줄인 수정은 아닙니다. 서버 준비 확인은 최대 180초, 그 뒤 프로필 조회는 최대 30초이며 서버 상태에 따라 최종적으로 실패 안내가 나올 수 있습니다.
- 앱의 `/status` 정상 응답이 공식 API·DB의 모든 동작을 보장하지 않습니다. 이후 실제 조회 단계의 오류 처리도 필요합니다.
- 이번 수정은 메인 검색 흐름이 대상입니다. 별도 상세 주소로 바로 접속하는 흐름 전체의 기동 대기 개선을 완료했다고 간주하지 않습니다.
- 백엔드 코드를 바꾸지 않아 백엔드 테스트는 이번에 재실행하지 않았습니다.

### 다음 변경 시 반드시 확인할 기준

1. 따뜻한 서버의 성공 요청만 확인하고 끝내지 않습니다. 절전/시작 중 상태, HTML 응답, 503을 포함합니다.
2. 서버가 준비되기 전에는 프로필 요청이 나가지 않아야 합니다. 준비 대기와 프로필 요청은 각각 유한한 제한 시간이 있어야 합니다.
3. 준비 중과 조회 중 모두 취소할 수 있어야 합니다. 취소·실패·시간 초과 후에는 로딩이 끝나고 재검색할 수 있어야 합니다.
4. 새 검색과 화면 이탈은 이전 요청을 중단해야 하며, 이전 응답이 새 검색의 결과·오류·로딩 상태를 덮어쓰면 안 됩니다.
5. 운영의 정상 상태 응답 하나만으로 공식 API나 특정 캐릭터 조회 성공을 단정하지 않습니다. 실데이터 검증과 모의 검증을 구분합니다.

관련 로직을 변경하면 다음 명령으로 회귀 테스트와 빌드를 실행합니다. 저장소 루트에서 프로젝트가 지원하는 Node 버전을 사용합니다.

```sh
node --test --test-reporter=dot frontend/tests/*.test.mjs
npm --prefix frontend run build
```

## 다음 오류 기록 양식

새 오류는 기존 사례를 덮어쓰지 않고 고유 번호로 추가합니다. 같은 원인이 재발하면 기존 번호에 발생일·원인 차이·보완 테스트를 덧붙입니다.

```text
ERR-00N — 증상 제목
기록일 / 발생 환경:
사용자 증상과 재현 조건:
확인한 사실과 로그·측정치(비밀 값 제외):
원인 판단 / 아직 확인하지 못한 부분:
수정 파일과 선택 이유:
수정 커밋:
테스트 명령과 실제 결과:
운영 검증 여부 / DB에 미치는 영향:
남은 한계:
재발 방지 기준과 추가한 회귀 테스트:
상태 / 다음 작업:
```
